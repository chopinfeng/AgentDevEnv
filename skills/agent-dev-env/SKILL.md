# Agent 开发环境搭建

把一个能跑的 Agent demo 变成能长期演进的产品，难点不在模型调用，而在**边界划分**：什么该冻结、什么该可换、什么该隔离。这个 skill 给出这些边界的划法，以及为什么这么划。

## 这个 skill 不做什么

具体平台的 API 细节由专门的 skill 覆盖，不要在这里重复造轮子。**先检查会话里有没有这些 skill，有就直接用：**

| 需要做的事 | 用哪个 skill |
|---|---|
| Cloudflare 平台细节（Workers/KV/D1/R2/Vectorize） | `cloudflare` |
| Agents SDK 的类与 API | `agents-sdk` |
| Durable Objects 状态与 WebSocket | `durable-objects` |
| wrangler 命令与配置语法 | `wrangler` |
| Workers 代码规范与反模式 | `workers-best-practices` |

本 skill 负责的是它们之上的一层：**架构决策**。决策定了，再去那些 skill 查怎么写。

## 开始之前：先问清三件事

不要直接开始搭。这三个答案会改变整个结构，猜错了返工成本很高：

1. **Agent 跑在哪** —— 边缘 isolate（TypeScript，冷启动快，但跑不了 Python 和长驻进程）还是容器（Python 生态、长任务，但有冷启动与常驻成本）？
2. **有没有物理设备** —— 涉及硬件的话，设备的角色边界要一开始就定死。中途加会推翻通信层。
3. **多人协作还是单人** —— 多人才值得上完整的三环境和审批流；单人项目上来就搞审批只会拖慢自己。

用户在场就直接问。**如果拿不到回答**（无人值守、批量任务），按这组默认值往下走并在交付时说明：边缘运行时、无设备、多人协作。这组默认值最容易在事后收窄——边缘设计可以靠「边界二」的 seam 退到容器，反过来则要重写。

## 核心边界

整套设计围绕五条边界。**每条边界的价值都在于"变更被挡在边界的一侧"**——理解这点比记住结构更重要。

### 边界一：环境隔离 —— 配置相同，实例不同

三个环境用**同一份配置文件**，只有资源实例和密钥不同。这样"在我机器上能跑"就不成立了，因为本地跑的就是同一份配置。

- 本地：全套服务跑在本机（模拟器 + 本地数据库容器）
- 测试：独立资源实例，合并主干自动部署
- 生产：独立资源实例，人工审批 + 灰度

数据库 schema 只经迁移文件变更，禁止在控制台手改——手改的那一次会让三个环境永久分叉。

细节与 CI/CD 流水线：`references/environments.md`

### 边界二：框架可换，环境不动

Agent 框架迭代很快，而部署底座不该跟着晃。中间用一层适配器契约隔开：

- **环境侧**（不变）：会话持久化、记忆读写、路由、部署配置、数据库 schema
- **框架侧**（可换）：给定「消息 + 历史 + 记忆」产出回复

换框架 = 改一个环境变量。**有状态运行时（如 Durable Objects）尤其要注意**：类名和迁移标签必须冻结，改动会触发数据迁移——这是最容易踩的坑。

契约定义、注册表写法、跑不进边缘的框架怎么接：`references/framework-seam.md`

### 边界三：工具与框架解耦

工具用**纯 JSON Schema** 描述，不绑任何 SDK。理由很实际：MCP 原生就是 JSON Schema，主流 TS/Python 框架也都接受它——这是唯一的公共格式。绑了某个 SDK 的工具定义，换框架时就要全部重写。

四类来源汇成一份工具集：MCP 服务器、物理设备、Skills、内建工具。加一类来源 = 加一个 provider，不动 Agent 代码。

- 工具层、MCP 接入（含 OAuth）、工具回调鉴权：`references/tools-and-mcp.md`
- Agent Skills 规范与渐进式披露：`references/skills.md`
- 知识库/RAG 接入（权限过滤、索引同步、出处）：`references/knowledge-base.md`

### 边界四：进化与执行分离

让 Agent 越用越好的机制（提示词优化、记忆积累、代码进化、RL 训练）**都不该在请求路径上跑**。线上采集 trace，离线跑优化，产物经 PR + 评估门禁回到线上。

这条边界同时是安全边界：自动优化的产物永不直接进生产。

评估集怎么建、轨迹评估、CI 门禁的统计方法、prompt 版本治理、四类进化机制：`references/evaluation-and-evolution.md`

### 边界五（仅硬件项目）：设备不做 Agent

MCU 跑不动有工具调用能力的模型。设备负责感知与执行，Agent 循环留在云端。这条边界定错了会导致固件反复重刷。

设备分层、两种接入方言、协议现状：`references/edge-devices.md`

## 产品化：从能跑到能上线

上面五条边界解决结构问题。**结构对了不等于能上生产**——Agent 比普通服务多两类失败：动作有副作用且可能重复，循环可能不收敛。

- 幂等、熔断与恢复探针、能力开关、循环护栏、人机协同的中断-恢复、**上线前对照清单**：`references/reliability.md`
- Prompt 缓存的静默失效、上下文管理、把 token 用量当告警信号：`references/cost-and-context.md`

诚实说明：**目前没有一份被行业公认的 Agent 上线检查清单。** `reliability.md` 里那份是从有出处的材料缝合的，可以用，但别当成标准。

## 已有项目：增量接入

用户项目已经在跑时，不要建议推倒重来。按需要什么读什么，各自独立：

| 用户想要 | 读这个 | 前置条件 |
|---|---|---|
| 接入 MCP 工具 | `references/tools-and-mcp.md` | 无 |
| 接入物理设备 | `references/edge-devices.md` + 上面那份 | 需要有状态运行时（如 DO）承载长连接 |
| 加 Skills | `references/skills.md` | 无 |
| 接知识库 / RAG | `references/knowledge-base.md` | 无 |
| 以后能换框架 | `references/framework-seam.md` | 抽 seam 时会动持久化边界，建议趁早 |
| 补测试环境 | `references/environments.md` | 现有配置要先改成同构形态 |
| 建评估体系 | `references/evaluation-and-evolution.md` | 无，且**应该最先做** |
| 上生产前检查 | `references/reliability.md` | 无 |
| 成本降不下来 | `references/cost-and-context.md` | 先确认缓存真的生效了 |

**先抽工具层再接具体工具。** 如果用户同时要 MCP 和设备，先把工具 provider 的结构立起来（半小时的事），再分别接——否则第二类工具接入时要重构第一类。

下面的「搭建顺序」是给新项目的，已有项目可跳过。

## 搭建顺序

按这个顺序做，每步都能独立验证，不会积累一堆没验证的假设：

1. **三环境骨架** —— 先把空 Agent 部署到三个环境，跑通 CI。此时还没有业务逻辑，但部署链路是通的。
2. **一个最小 Agent** —— 单轮对话 + 状态持久化。验证状态在重启后还在。
3. **框架 seam** —— 即使现在只有一个框架，也把契约先立起来。事后再抽成本高得多。
4. **工具层** —— 先内建工具，再 MCP，再设备。每加一类都验证工具清单里能看到。
5. **评估集** —— 这是后续一切优化的度量基准。没有它，"改进了"只是感觉。
6. **进化管线** —— 有了评估集才有意义。

脚手架脚本可以直接生成 1–4 步的骨架：

```bash
python3 <skill 目录>/scripts/scaffold.py <项目目录>
```

生成的骨架**可直接构建**（`pnpm install && pnpm typecheck` 通过，`wrangler deploy --dry-run` 能出包）：工作区配置、冻结契约、可运行的 DO 会话持久化、失败关闭的工具回调、三环境同构配置、CI 工作流、AGENTS.md。

**不生成**：业务逻辑、模型调用的接线（适配器里留了 TODO）、数据库 schema、前端、生产资源 ID。评估集是占位样例，**必须换成你的场景**。

参数：`--minimal` 单人项目（跳过 staging 与审批流），`--no-devices` 不含设备层，`--help` 看全部。目前只支持 Cloudflare 栈；其他栈按 `references/stacks.md` 的映射手工搭，边界不变。

## 容易做错的地方

这些是实践中反复出现的坑，每条都有具体代价：

**配置里只声明当前框架需要的变量。** 换框架时又得改配置，seam 就白留了。正确做法是一次性声明所有适配器所需变量的并集，空值也留着。

**未知框架名静默回落到默认值。** 一个拼写错误会让生产悄悄跑在另一个框架上，而且不报错——排查这种问题极其痛苦。应该立即失败并列出可选值。

**把会话状态放进业务数据库。** 高频读写的会话状态应该贴着计算放（如 DO 内置存储），业务数据才进主库。放反了延迟和成本都吃亏。

**工具执行端点不鉴权。** 如果工具能驱动物理设备或产生副作用，这个端点就是攻击面。生产环境没配密钥时应当**直接拒绝服务**，而不是放行——静默放行比报错危险得多。

**Skills 正文全塞进系统提示。** 违背渐进式披露，几十个 skill 就把上下文占满了。只让名字和描述常驻，正文按需加载。

**先做进化管线再做评估集。** 顺序反了，因为没有度量就无法判断进化是否有效，只能凭感觉。

## 技术栈映射

默认按 Cloudflare 全家桶给方案（边缘 Agent 的完成度最高）。用其他栈时，边界不变，只是组件换名字——各栈的对应关系见 `references/stacks.md`。
