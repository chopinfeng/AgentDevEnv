# 实测基线

首轮，2026-09-01。后续迭代与这份对比。

## 任务 eval

只跑了 `greenfield-scaffold`（唯一带可程序化断言的用例；其余四条是主观断言，需人工或 LLM 评判）。

同一条 prompt 交给两个全新会话，一个有 skill 一个没有：

| 断言 | 有 skill | 基线 | 区分度 |
|---|---|---|---|
| 产出可安装可类型检查 | ✓ | ✓ | floor |
| 三环境 DO class_name 一致 | ✓ | ✓ | floor |
| 存在框架适配器契约 | ✓ | ✗ | **differentiator** |
| 未知框架名不静默回落 | ✓ | ✗ | **differentiator** |
| 环境变量面是并集 | ✓ | ✗ | **differentiator** |
| | **5/5** | **2/5** | |

**怎么读这个结果**：真正说明问题的是那 3 条 differentiator。用户明确说了「以后可能要换框架」，基线组交付了一个结构合理、能构建的 monorepo，但**没有框架 seam**——换框架时要重写。三条差异全部落在 skill 的核心主张上。

两条 floor 断言在两组都通过，说明一个称职的 agent 本来就会做对（能构建、DO 类名一致）。它们不体现 skill 价值，留着是**防脚手架自身回归**——早期版本的脚手架就曾生成过装不上的项目。

### 断言的自检

断言必须能判失败才有意义。用故意违反每条冻结项的反例验证过：

- 正例（脚手架产出）：5/5 通过
- 反例（class_name 三环境不一致、静默回落、缺 seam）：0/5，且能精确指出是哪个环境的 class_name 不一致

### 过程中修掉的两个断言 bug

都是「看起来在测、其实没测」的类型，值得记下来：

1. **`content_absent` 在空目录上平凡通过** —— 没有文件可扫也算「未出现」，空产出能拿满分。改为：扫到 0 个文件时判为无法判定，不计通过。
2. **花括号 glob 不生效** —— `**/*.{ts,py,md}` 在 `pathlib.glob` 下静默匹配 0 个文件，那条 ACL 安全断言实际上一直没跑。加了花括号展开。
3. **ACL 断言有假阳性** —— 原正则会把服务端的 `acl: ctx.identityFromGateway`（正确用法）误判成违规。收紧为「身份键出现在 schema 的 properties 里且被声明成对象」。

## 触发 eval

20 条，每条 1 次（冒烟档；正式评估建议 `RUNS=3`）。

**首轮：17/20**

- 负例 **10/10** —— 近似误判全部正确拒绝，包括「帮我写一个 MCP server」「帮我搭 React 脚手架」「我的 ESP32 连不上 WiFi」「帮我写一个 skill」「LangGraph 的 StateGraph 怎么加条件边」。特异性没有问题。
- 正例 7/10，漏触发三条：

| 漏触发的 query | 原因 |
|---|---|
| 内部 agent 接 confluence 知识库，不同部门权限不一样 | **真实疏漏**——加了 `knowledge-base.md` 却忘了更新 description |
| agent 项目怎么组织，都堆在一个 index.ts 里两千多行 | 概念在（「规划工程结构」）但用户是**描述症状**而非点名 |
| 这个月 api 账单翻了三倍 | 同上，「控制成本」在描述里，但用户说的是账单异常 |

修法：补上知识库/RAG 与权限隔离；把「规划」扩成「规划或重构工程结构与代码分层」、「控制成本」扩成「排查 token 消耗或账单异常」；末尾加一句点明用户常只描述症状。

**没有做的**：把失败 query 的关键词直接抄进 description。那是过拟合——换个说法照样漏。改的是概念范畴。

**改后第二轮：20/20**（正例 10/10，负例仍 10/10）。三条漏触发全部修复，且特异性没有牺牲——补充概念范畴没有把负例也拉进来。

## 这份基线的局限

写在这里免得后来的人（包括我自己）高估它：

1. **`RUNS=1` 是冒烟档**，不是统计上可靠的结果。模型有随机性，正式评估要 `RUNS=3` 以上取触发率。
2. **触发 eval 没有留出测试集。** 20 条全部用于观察失败并据此改 description，属于在同一批数据上调优。严格做法是 60/40 切分、只用训练集指导修改、按测试集选版本。20/20 因此更像「这批用例上不再犯错」，而非泛化能力的证明。
3. **任务 eval 只有 1 条跑了对比**，另外 4 条全是主观断言，尚未评判。
4. **基线那次运行在末尾遇到 API 错误提前终止**——它已经产出了可评分的完整项目（37 个文件、能构建），但若继续跑或许会补上更多。2/5 这个数字应当理解为下界。

下一轮值得做的：给触发 eval 做训练/测试切分并跑 `RUNS=3`；给剩下 4 条任务 eval 跑对比并用 LLM 评判主观断言。
