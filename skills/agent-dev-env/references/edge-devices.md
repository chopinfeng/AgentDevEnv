# 低算力设备接入

## 第一条边界：设备不做 Agent host

MCU 上跑不动有实用价值的模型。实测数据（2026-08 核实）：

- ESP32-S3 上 **260K 参数**模型约 19 tok/s，项目作者自评"能跑但没什么用"
- **29M 参数**模型约 9.5 tok/s（逐层从 Flash 流式读取）

这个量级没有指令跟随和工具调用能力，与 Agent 无关。**设备负责感知与执行，Agent 循环留在云端。**

这不是保守估计——目前唯一有数万台规模验证的形态（xiaozhi-esp32，29.5k stars）正是这个架构：设备做音频采集与本地工具，云端做 ASR + LLM + TTS。

## 设备分层

| 层 | 硬件 | 角色 | 注意 |
|---|---|---|---|
| Tier 0 | ESP32 / MCU（400–520KB SRAM） | 纯工具提供方 | 固件只需 WiFi + WebSocket + JSON |
| Tier 1 | 树莓派 4/5（8–16GB） | 可跑本地 MCP servers、本地窄任务模型 | 主推理仍走云 |
| Tier 2 | 云端 | Agent 循环、工具汇总、持久化 | —— |

**树莓派的本地模型边界**（Pi 5 + Ollama 实测）：Gemma3:1b 约 12 tok/s，Qwen2.5:1.5b 约 10 tok/s，3B 类模型 4–6 tok/s 且**长 prompt（5000+ token）会超时**。结论：本地模型只适合窄任务（意图分类、离线兜底），主推理走云。

瓶颈是内存带宽不是算力——每生成一个 token 要把全部权重过一遍内存。

## 通信设计

设备通过 WebSocket 长连接挂到自己的 Agent 实例，能力暴露成工具。

**Hibernation 是关键**：用支持休眠的 WebSocket（Cloudflare 的 hibernatable WebSocket），设备挂着长连接空闲时不产生计算费用，有帧到达自动唤醒。没有这个特性，常驻在线的设备会一直计费——这决定了方案能不能规模化。

配套的固件纪律：**不要定时刷帧**。每一帧都会唤醒休眠的实例并计费。改成阈值触发上报（温度变化超过 1°C 才发），或者拉长心跳间隔。

### 设备身份必须持久化

把设备身份和方言存进**连接状态**（随 hibernation 持久化），并用**连接标签**区分设备连接与普通客户端连接。

**不要放进内存 Map。** 实例休眠醒来后内存全空，设备还连着但云端不知道它是谁——现象是「Agent 说没有这个工具，但设备明明在线」，且只在休眠后复现，很难查。

### 设备绑定到哪个实例

这是必须提前定死的架构决策，改起来要动固件。

连接串里的 `<session>` 决定设备挂在哪个 Agent 实例上。矛盾在于：**共享设备**（办公室的传感器）和**每用户一个实例**的会话模型天然冲突。

三种解法，按复杂度排：

1. **设备走独立 session**（如 `devices-office`），需要用它的会话通过实例间 RPC 转发调用。推荐——设备生命周期与用户会话解耦
2. **每个用户实例各自连一份**，设备要维持 N 条连接。只适合设备数少且用户数固定
3. **单一全局会话**，所有人共用一个 Agent 实例。最简单，但没有会话隔离

选哪个取决于「这台设备是属于某个人的，还是属于场地的」。

## 两种方言

```
wss://<host>/agents/<agent>/<session>?role=device&dialect=<min|mcp>&device=<id>
```

### min —— 自定义极简帧

设备不实现 MCP。固件约 200 行，无 JSON-RPC、无 schema 协商、无 session。

```
设备 → 云  {"t":"hello","device":"lamp-01","tools":[{name,description,schema}]}
云 → 设备  {"t":"invoke","id":"7","tool":"set_lamp","args":{...}}
设备 → 云  {"t":"result","id":"7","ok":true,"data":"已开灯"}
设备 → 云  {"t":"event","name":"motion","data":{...}}      // 主动上报
```

工具 schema 用编译期常量字符串，不占堆——MCU 上这点重要。

适合：传感器、执行器这类窄能力设备。

### mcp —— JSON-RPC 信封

MCP 消息包在信封里，**设备是 MCP Server，云端是 MCP Client**（角色是反直觉的）：

```json
{ "type": "mcp", "payload": { "jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {...} } }
```

云端连上直接发 `tools/list` 拉能力清单——现行规范已移除 `initialize` 握手，不需要握手。

适合：已在跑 Espressif 官方 `mcp-c-sdk` 或小智固件的设备。

> **注意**：Espressif 官方 SDK 默认协议版本是 `2025-11-25`，属于**握手时代**，落后现行 `2026-07-28` 规范一个大版本。对接时需要做版本探测与 fallback。

## 协议合法性

WebSocket **不是** MCP 官方 transport，提案已关闭为 dormant，不会进规范。所以两种方言都属于规范明确允许的 **custom transport**。

规范对此有明确指引：跑在可靠双向字节流上的 custom transport **SHOULD 复用 stdio 的换行分隔 JSON-RPC framing**，而不是自创一套。按一帧一行 JSON 走即可。

## 可靠性

设备会掉线、会睡眠、会卡在阻塞操作里。工具调用必须：

- **设超时**（15 秒量级）。MCU 无响应是常态，不是异常
- **掉线时让在途调用立即失败**，而不是挂到超时——用户体验差别很大
- **调用与回执用 id 配对**，迟到的回执直接丢弃

主动上报的事件落库，供后续对话引用和进化管线取用。

### 离线设备要「可见地缺席」

设备掉线后如果只是把工具从清单里删掉，模型看到的是「从来没有这个能力」，于是回答「我没法读温度」——而正确答案是「传感器离线了」。这两句对用户的价值完全不同。

两种处理，选一种：

- **保留工具但标注离线**，调用时返回明确的「设备 X 当前离线」错误。模型能据此给出准确说明
- **提供一个 `list_devices` 内建工具**，在系统提示里引导模型「设备相关问题先查在线状态」

配一个排查类 skill（见 `skills.md`）效果更好——把「先查在线、超时通常是固件卡住、错误信息原样转述」这类经验固化下来。

## 鉴权

**设备接入端点必须鉴权。** 这一点和 HTTP 工具回调端点同等重要，甚至更暴露：任何人连上这个 WebSocket URL 就能注册任意工具，而你的 Agent 会去调用它们——等于把工具注入的权限开放给了公网。

做法与工具回调一致：校验连接串或 header 里的设备密钥，**生产环境未配密钥时直接拒绝连接**，不要放行。设备密钥应当逐设备签发，便于单独吊销。

## 其他安全面

设备工具直接暴露 shell 是高风险面——**云端 Agent 的输入可能来自任意用户**，不能默认可信。树莓派这类能跑 shell 的设备，命令必须走白名单，且只放只读命令。

涉及执行器（继电器、电机）的操作，考虑加人工确认环节。
