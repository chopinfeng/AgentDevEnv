# 评估与进化

## 先建评估集，再谈优化

没有评估集，"改进了"只是感觉。任何提示词调整、模型更换、框架切换都无法判断是变好还是变坏——这是 Agent 项目最常见的失控来源。

**评估集应该来自真实 trace，不是拍脑袋编的。** 上线后从线上采样，挑出成功的、失败的、边界的各若干条，标注期望行为。

一份可用的评估集包含：

```jsonl
{"input": "...", "expected_traits": ["准确", "一句话", "承认不确定"], "tags": ["faq"]}
{"input": "...", "expected_tools": ["list_devices"], "tags": ["device"]}
```

两类断言分开处理，因为可靠性不同：

- **硬指标**（可程序化校验）：是否调了预期工具、输出是否合法 JSON、是否在 N 步内收敛、延迟与 token 是否超预算。这类断言稳定，适合做 CI 门禁。
- **软指标**（LLM-as-judge）：语气、是否答到点上、是否恰当承认不确定。这类有波动，**同一条跑多次取通过率**，不要用单次结果卡门禁。

## 评轨迹，不只评终答

这是近年最明确的共识转向：**只看最终回答会漏掉大量问题**。同样一句正确回答，可能来自「一次命中」，也可能来自「试错 12 轮、调了 3 个不该调的工具」——后者在成本、延迟和可靠性上都是隐患，但终答评估看不出来。

主流框架都把轨迹评估做成了一等公民（LangSmith 的 trajectory evaluators、Microsoft Foundry 的 ToolCallAccuracy、Vertex 的 trajectory 指标）。常见的几种匹配模式：

- **严格匹配**：工具调用与参考完全一致且同序
- **无序匹配**：调用集合相同，顺序无关（多数场景该用这个）
- **子集**：只允许调用参考里出现过的工具——**用来抓「多调了不该调的工具」**
- **超集**：必须调用参考工具，允许额外

除了匹配，还值得单独看：工具选择是否合理、错误后能否恢复、遇到信息不足时会不会主动追问。

## LLM-as-judge 怎么用才可靠

已知的系统性偏差有三类：位置偏差（偏好靠前的答案）、冗长偏差（偏好长答案）、**自我偏好**（偏好自己生成的内容）。

对应的缓解手段：

- pairwise 比较做**位置轮换后聚合**
- judge 与被测模型**不同源**，避开自我偏好
- 与人工标注算一致度（Cohen's κ），**先验证可靠性再规模化**

rubric 写法：让 judge 只输出**离散标签**（correct/incorrect 或 1–5），不要纯定性评价；标准具体到可机械判定；先让模型推理再出分，然后丢弃推理。

## 门禁怎么设

放进部署流水线，部署到测试环境后自动跑。

- 硬指标：**全部通过**才算过。回归就是 bug
- 软指标：与基线比，而不是与绝对分数比

**不要用「单次分数掉了就拦截」**——评估本身有噪声，这样会被反复误报，最后团队就开始无视门禁了。

正确做法：

1. **配对比较** —— 新旧版本跑**同一批样本**，比逐样本的 delta，消除样本间方差
2. **同题多次采样取平均** —— 研究表明同题重采样的波动通常大于换样本的波动，所以多采样比单纯加样本量更划算
3. **对 delta 报置信区间**（bootstrap），区间完全落在 0 一侧才判为真回归

固定 seed 与温度能减少一部分噪声，但消不掉。

## Prompt 版本治理

**版本不可变，标签才是部署指针。** 这个设计的价值在于：「生产跑哪个版本」变成数据问题而非代码问题——**回滚 = 把 `production` 标签指回上一版本，不需要重新部署应用**。

实现上：

- 每次改动生成不可变版本，递增版本号
- 用标签（`production` / `staging` / `canary`）指向具体版本
- 响应体回显当前版本号，出问题能立刻定位
- 标签指针放快存储（KV 之类），秒级生效

**注意**：多数 prompt 平台**不替你切流量**——canary 的百分比路由是应用代码的事。平台给的是「按版本看质量/成本/延迟」的观测能力。

常见折中：prompt 源文件仍进 Git（保留 review 与审计），运行时解析走标签；CI 在合并时推新版本并打 `staging` 标签，评估通过后再移 `production` 标签。

## 采集什么

进化管线的原料来自线上：

- LLM 网关的调用 trace（提示词、响应、token、延迟）
- 工具调用记录（调了什么、成功与否、耗时）
- 人工反馈（用户评分、客服标注）——这是最贵也最有价值的信号
- 设备事件（硬件项目）

归档到对象存储（出口流量费低的那种）。**注意脱敏**：trace 里可能有用户隐私，进评估集前要过一遍。

## 四类进化机制

它们与运行时约束正交——这决定了架构必须分层。**按投入产出比排序**：

| 机制 | 代表 | 产物 | 在哪跑 | 建议 |
|---|---|---|---|---|
| **① 提示词/程序优化** | DSPy + GEPA、EvoAgentX | 优化后的提示词 | 离线批处理（Python） | **投入产出比最高，第一优先**。产物可部署到任何运行时 |
| **② 记忆积累** | Letta、Skills、技能库 | 记忆条目 / 新 skill | 在线 | 第二优先。最容易在有状态运行时上自建 |
| **③ 代码进化** | OpenEvolve、DGM | 优化后的代码 | 沙箱 + 大量算力 | 选择性投入，用于关键算法 |
| **④ RL 训练** | Agent Lightning、AgentEvolver | 模型权重 | GPU 集群 | 远期。与部署解耦 |

「边缘原生 + 自进化」目前没有现成框架——进化框架基本都在 Python 服务器侧。可行架构是**边缘执行 + 离线进化管线**。

## 闭环

```
线上 trace + 人工反馈
    ↓ 归档
对象存储
    ↓ 定时触发
离线优化（容器 / GPU）
    ↓ 产物以 PR 提交
评估门禁（staging）
    ↓ 人工审批
灰度放量 → 生产
```

## 安全边界

**进化产物永不直接进生产。** 一切自动优化的提示词、代码都必须经过评估门禁 + 人工审批的 PR 流程。

这既是质量闸，也是对自改型 Agent 的控制面。代码进化类实验一律限制在沙箱内运行。

配套的工程实践：

- 提示词**版本化**，递增版本号，响应体回显当前版本——出问题能立刻定位是哪一版
- 版本指针放 KV 之类的快存储，**可秒级回滚**，不用重新部署
- 每次进化产物的评估结果留档，形成可追溯的改进曲线

## 成本控制

Agent 的 token 消耗容易失控，尤其是多轮工具调用：

- **限制单回合步数**（`stopWhen: stepCountIs(N)`），防止工具调用死循环
- LLM 网关开缓存（开发环境尤其值），设限流与成本告警
- 评估集跑起来也烧钱——CI 里跑精简集，完整集定时跑
- 长上下文考虑摘要压缩，但要评估摘要带来的质量损失
