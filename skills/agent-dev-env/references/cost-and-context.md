# 成本与上下文

Agent 的 token 消耗比单轮对话高一个量级——多轮工具调用会把历史反复重发。这里是几个杠杆最大的点。

> 具体价格与阈值变动频繁，本文只讲**机制与陷阱**。数字以各家官方文档为准，链接见 `sources.md`。

## Prompt 缓存：最大的杠杆，也最容易静默失效

缓存命中的输入通常按基础价的一小部分计费（Anthropic 为 0.1×，其他家量级相近），对 Agent 这种「系统提示 + 工具定义 + 长历史反复重发」的形态收益极大。

**三家共同的最大陷阱：前缀低于最小可缓存 token 数时不会报错，只是静默不缓存。** 这是「我加了缓存但没省钱」的头号原因。

各家的最小 token 阈值不同（且随模型不同），务必查当前文档。**验证方式**：看响应的 `usage` 里 `cache_read_input_tokens` / `cache_creation_input_tokens` 是否真的有值——不要假设配了就生效。

### 缓存失效的连锁反应

Anthropic 的失效层级是 **tools → system → messages**，上层变动会让下层全部失效。这意味着：

- **动态增删工具会击穿整个缓存**。设备上线下线导致工具集变化时尤其要注意——这正是本架构的设备层会遇到的情况
- 工具定义、citations 开关、thinking 参数、`tool_choice` 等的变动同样失效
- 缓存断点数量有限（Anthropic 为 4 个/请求）

**实践建议**：把稳定的部分（系统提示、核心工具）放前面，易变的部分（设备工具、当前上下文）放后面，让缓存边界落在稳定/易变的交界处。

### Gemini 的隐性成本

Gemini 的缓存**按小时收存储费**。长 TTL + 大上下文的场景，存储费可能吃掉全部节省，必须单独建模。其他家目前不这样收。

## 批处理

Anthropic / OpenAI / Gemini 的 Batch API **均为 50% 折扣**，窗口 24 小时。

适合：评估集回归、离线进化管线、数据标注。**不适合**：任何在请求路径上的调用。

注意 Anthropic 的批内不支持 `max_tokens: 0` 的缓存预热技巧。

## 上下文管理

长任务 Agent 的上下文会持续膨胀直到超限。三种手段：

- **上下文编辑**：接近上限时自动清除陈旧的工具调用与结果。Anthropic 公布的评估中，这让原本会因上下文耗尽而失败的工作流得以完成，同时显著降低 token 消耗
- **记忆外置**：跨会话的文件式外存，存储后端由你掌管
- **just-in-time 加载**：上下文里只放轻量标识符，运行时按需拉取，而不是把完整数据对象塞进去

第三条最重要也最容易被忽略。**不要把整个数据库查询结果塞进上下文**——给 Agent 一个查询工具，让它按需取。Skills 的渐进式披露是同一个思路。

## 把 token 用量当告警指标

**token 用量突增通常是循环、失控重试或上下文膨胀的第一个征兆**，比事后看账单早得多。

建两个指标：

- **token / 请求** —— 抓单次异常
- **token / 任务完成** —— 抓效率退化（同样的任务花更多轮次才做完）

第二个更能反映质量问题：模型变笨或提示词改坏时，它会先于准确率指标恶化。

## 模型路由

用小模型处理简单请求、大模型处理复杂请求，是有效的降本手段（学术上有 RouteLLM 等工作）。

但要注意：**网上流传的具体节省比例多数没有可靠来源**，且高度依赖任务分布。要用就自己在真实流量上测，别照搬别人的数字。

路由器本身也有成本和延迟，简单场景不如直接用便宜模型 + 兜底升级来得实在。
